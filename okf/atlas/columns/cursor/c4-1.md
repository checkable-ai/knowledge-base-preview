## Answer

Not covered. Cloud Agent OIDC tokens (RS256 JWT) carry cloud_agent_id, owner (user or service account), team, agent_runtime, worker_id, repository, branch, environment and automation claims, but no claim for agent version, release or build, so identity is not tied to the release the agent is. Local IDE and CLI agents run as the signed-in user with no separate agent identity. The token identifies a run, not a process.

Research detail: Each Cloud Agent run gets a short-lived RS256 OIDC token carrying cloud_agent_id, the owning user or service account, team and repository claims. Service accounts give automations an owner that is not a person. Local IDE agents run as the signed-in user with no separate agent identity.

## Products

Cloud Agent OIDC tokens, Service accounts

<!-- chunk: gaps -->
## Gaps

No agent identity for local agents. Tokens identify the run, not a process, and any process that reaches the socket can mint one. No link to a release or agent version.

<!-- chunk: options -->
## Options

Verify tokens against Cursor's JWKS and bind trust policies to sub and owner claims. Use one service account per workflow.
