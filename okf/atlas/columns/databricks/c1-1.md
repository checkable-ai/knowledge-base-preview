## Answer

Partly covered. Databricks documents managed Omnigent as a layer over Claude Code, Codex, Cursor and custom agents that keeps them 'in check with policies and sandboxing'. The built-in policies it supports, documented on omnigent.ai (built by the Databricks AI team and linked from the Databricks page), govern what an agent may do locally. ask_on_os_tools asks before any file or shell operation, read_only_os blocks file-changing tools, blast_radius sorts shell commands by risk, and worktree_guard limits writes. The OS sandbox restricts commands and file operations. These meet the outcome. The validity checker looked only at Databricks Sandbox, so the adversary's objection holds.

Source statement: "Omnigent on Databricks supports the built-in contextual policies and custom policies written in Common Expression Language (CEL)." (https://docs.databricks.com/aws/en/omnigent/)

Research detail: Databricks Sandbox runs agent-written code as the requesting user by default or as the app service principal, and agent.toml tool policies can downscope sandbox table access to read only. Supervisor Agent's built-in code tool runs in a sandbox with no internet access and only the tables and volumes added.

<!-- chunk: products -->
## Products

Databricks Sandbox, agent.toml tool policies, Supervisor Agent code execution tool

<!-- chunk: gaps -->
## Gaps

Sandbox network egress is unrestricted and not configurable. Sandbox is Beta. No documented per-command or file system scope controls inside the sandbox.

<!-- chunk: options -->
## Options

Keep sensitive data out of sandboxes, use downscope policies, and wait for egress controls before using Sandbox with untrusted code.
