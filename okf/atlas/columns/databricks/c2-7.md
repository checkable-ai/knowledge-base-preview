## Answer

Not covered. Network policies restrict egress for apps and serverless workloads (Enterprise tier), but the vendor documents no egress control for the Beta Sandbox, no immediate effect of policy changes (apps need redeploy or restart), no cancellation of in-flight runs, and no single stop across all agents.

Research detail: Databricks Sandbox, in Beta, runs untrusted code in an isolated environment separate from Agent Runtime, with a fixed 4 vCPU and 8 GB size, closed ingress and storage outside the home directory deleted on stop. Agent Runtime runs the agent server on Databricks Apps, where the agentbricks CLI can stop, start or delete a deployment and the app service principal gets only the grants that agent.toml declares. Network policies on the Enterprise tier enforce egress restrictions on apps and other serverless workloads, with a dry-run mode and denied attempts logged in system.access.outbound_network.

<!-- chunk: products -->
## Products

Databricks Sandbox, Agent Runtime on Databricks Apps, agentbricks deployments stop and delete, serverless network policies, network connectivity configurations

<!-- chunk: gaps -->
## Gaps

Databricks states sandbox egress has no restrictions and is not configurable. The Agent Runtime page does not describe cancelling an in-flight durable run, and interrupted runs are designed to recover. Network policies need the Enterprise tier. No documented control halts every running agent in a workspace at once.

<!-- chunk: options -->
## Options

Keep untrusted code execution out of the Sandbox until egress is configurable, or run it on serverless compute under a network policy. Test that agentbricks deployments stop ends an active durable run without it resuming. Rehearse revoking the app service principal as an emergency stop.
