## Answer

Covered. Grok Bot, Enterprise plan only. Network Controls default to allow-all until an admin sets a policy. Cutting access takes admin steps: remove the member or turn off Grok Bot for their group, and revoke sessions in the identity provider.

Source statement: "It stops running Bots, keeps the durable disk, and the member's next session starts a fresh computer." (https://docs.x.ai/grok-bot/security)

Research detail: The API code execution tool runs in an isolated environment with no external network or file system access and no persistence. Grok Build sandbox profiles use Landlock or Seatbelt to limit file access and child-process network, and a managed requirements.toml can pin a profile. Grok Bot Enterprise admins can terminate a member's computer to stop running bots and set network destination allowlists. API keys can be deleted through the Management API.

<!-- chunk: products -->
## Products

Code execution sandbox, Grok Build sandbox profiles, Grok Bot Network Controls and computer termination, Management API key deletion.

<!-- chunk: gaps -->
## Gaps

The Grok Build sandbox is off by default, and child-network blocking works on Linux only and does not cover model API or web tools. Grok Bot network policy and termination are Enterprise only. Key revocation timing is not documented.

<!-- chunk: options -->
## Options

Pin a strict sandbox profile through requirements.toml, use Enterprise network controls, and test how fast a deleted key stops working.
