## Answer

Not covered. No on-behalf-of token exchange to downstream systems; OIDC claims only identify the requester.

Research detail: OIDC tokens carry requesting_user_id and requesting_user_email so downstream trust policies can act on the initiating user. Service users can create sessions on behalf of a user with create_as_user_id, gated by the Impersonate Sessions permission, and Run Personal Automations lets automations run as the user. Repository actions use the organisation's Git integration rather than the user's own delegated authority.

<!-- chunk: products -->
## Products

OIDC claims, create_as_user_id, Run Personal Automations

<!-- chunk: gaps -->
## Gaps

No OAuth on-behalf-of token exchange to downstream systems. Audit for create_as_user_id sessions is attributed to the service user.

<!-- chunk: options -->
## Options

Write cloud trust policies on requesting_user claims and restrict Impersonate Sessions to named service users.
