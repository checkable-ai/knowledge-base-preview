## Answer

Covered. AgentCore Runtime. Sessions are not mapped to users, so the client tracks session IDs. There is no single agent-wide kill switch. Cutting access at once relies on IAM or resource policy deny plus StopRuntimeSession.

Source statement: "Each session in AgentCore Runtime receives its own dedicated microVM with isolated compute, memory, and filesystem resources." (https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html)

Research detail: AgentCore Runtime gives each session its own microVM with isolated compute, memory and filesystem, and terminates and sanitises it at session end. The StopRuntimeSession API stops a running session, and sessions also stop on idle timeout or maximum lifetime. Code Interpreter runs in a sandbox with a choice of Sandbox or Public network mode, and VPC connectivity puts Runtime and tools behind customer security groups.

<!-- chunk: products -->
## Products

AgentCore Runtime, StopRuntimeSession, AgentCore Code Interpreter, AgentCore VPC connectivity, IAM

<!-- chunk: gaps -->
## Gaps

AgentCore does not map sessions to users, so the client must track which sessions to stop. Revoking access for all sessions of one agent relies on IAM changes, with no single documented agent-wide kill control.

<!-- chunk: options -->
## Options

Script a stop of every session for an agent plus an IAM deny, and time how quickly in-flight tool calls end.
