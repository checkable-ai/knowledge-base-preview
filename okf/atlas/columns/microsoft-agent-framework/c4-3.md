## Answer

Covered. Foundry-hosted agents only, in user-invoked scenarios where a user token is present (Microsoft 365 channels such as Teams). Tools must be connected through a Foundry toolbox (FoundryToolbox, prerelease Python hosting package; AddFoundryToolboxes in .NET) with per-user OAuth consent. Subject to Entra ID tenant policies.

Source statement: "In this case, the agent can call downstream services on behalf of the user using the user's delegated permissions, subject to Microsoft Entra ID tenant policies." (https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)

Research detail: In Foundry hosting the platform supplies the caller's user context, and FoundryToolbox forwards it for per-user identity passthrough with OAuth consent requests surfaced to the user. Foundry documents OAuth On-Behalf-Of when a user token is present in Microsoft 365 channel scenarios. Self-hosted agents must derive and propagate identity themselves.

<!-- chunk: products -->
## Products

Foundry Hosted Agents integration, FoundryToolbox, oauth_consent_request handling

<!-- chunk: gaps -->
## Gaps

No OBO helper in the core SDK for self-hosted deployments. OBO for non-Microsoft 365 entry points is not described.

<!-- chunk: options -->
## Options

Use Foundry hosting with Toolbox for delegated tool access, or implement OBO token exchange in a header_provider for self-hosted MCP tools.
