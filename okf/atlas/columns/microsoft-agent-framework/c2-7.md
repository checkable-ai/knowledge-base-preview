## Answer

Covered. Sandbox limits: DockerShellTool (beta, Docker or Podman) or Foundry per-session VM isolation with configured network isolation. Stop: Foundry-hosted agent, authorised management access. Disable is reversible, delete is permanent and terminates active sessions.

Source statement: "Disable an agent to take its endpoint offline without deleting the agent or any of its versions." (https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/manage-hosted-agent)

Research detail: DockerShellTool runs model-generated commands in an OCI container that by default disables networking, runs as non-root, uses a read-only root filesystem, drops capabilities and caps memory at 512 MiB and processes at 256, and rejects run arguments that weaken these. Hyperlight CodeAct runs generated code in a hardware-virtualised microVM restored from a clean snapshot each run, with a read-only /input tree and an outbound allow list. LocalShellTool enforces a 30-second timeout and terminates child process trees, and close() rejects queued commands.

<!-- chunk: products -->
## Products

DockerShellTool, Hyperlight CodeAct provider, LocalShellTool

<!-- chunk: gaps -->
## Gaps

The shell tools package and Hyperlight connector are beta or preview, and the .NET Hyperlight package cannot restore yet. LocalShellTool is not a sandbox. Host tools reached through call_tool run outside the sandbox with host credentials. The SDK has no documented single kill switch that stops a running agent or revokes its credentials.

<!-- chunk: options -->
## Options

Use DockerShellTool or Hyperlight for untrusted code, keep approval on, hold credentials in narrow host tools, and wrap runs in cancellation and credential revocation owned by the host application.
