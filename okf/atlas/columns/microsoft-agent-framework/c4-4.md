## Answer

Not covered. The core SDK and its A2A client and hosting packages document no authentication or authorisation of agent-to-agent calls across trust boundaries, and leave it to the host application. The nearby Foundry Agent Service A2A tool can authenticate with an agent identity, but that is a Foundry tool feature and not a documented Agent Framework feature.

Research detail: A2AAgent connects to remote A2A agents and accepts an AuthInterceptor for secured endpoints. The A2A hosting packages leave authentication to the application and the docs say a production host must authenticate callers and authorise task, context and cancellation IDs. Foundry hosted agents expose an A2A endpoint authenticated with Entra ID.

## Products

A2AAgent client, agent-framework-a2a and agent-framework-hosting-a2a, Foundry hosted A2A endpoint

<!-- chunk: gaps -->
## Gaps

Self-hosted A2A servers have no built-in authentication or authorisation. Default task stores are in-memory.

<!-- chunk: options -->
## Options

Front self-hosted A2A endpoints with an identity-aware gateway and an owner_resolver tied to the trusted tenant and subject, or host on Foundry.
