## Answer

Not covered. The framework has no documented feature that authenticates and authorises agent-to-agent calls across defined trust boundaries. On the A2A server page, the application has to assemble the A2A SDK server itself, including authentication. Forwarded metadata is described as not being an authentication boundary. Three nearby features fall short. First, the Python A2AAgent client can attach a bearer token through an auth_interceptor, but this only sends a credential and does not check it. Second, Foundry Hosted Agents give each agent its own Entra identity for reaching models, tools and downstream services. Third, Foundry Agent Service endpoint authorisation (AzureRbac, and AgentBlueprint, which is in preview) controls access for any caller at the caller-to-agent boundary. Those last two belong to the separate Foundry Agent Service, not the framework, and neither is documented as agent-to-agent trust-boundary authorisation.

Last checked 15 November 2026. This platform is checked on demand, so this answer has not been rechecked since.

Research detail: A2AAgent connects to remote A2A agents and accepts an AuthInterceptor for secured endpoints. The A2A hosting packages leave authentication to the application and the docs say a production host must authenticate callers and authorise task, context and cancellation IDs. Foundry hosted agents expose an A2A endpoint authenticated with Entra ID.

## Products

A2AAgent client, agent-framework-a2a and agent-framework-hosting-a2a, Foundry hosted A2A endpoint

<!-- chunk: gaps -->
## Gaps

Self-hosted A2A servers have no built-in authentication or authorisation. Default task stores are in-memory.

<!-- chunk: options -->
## Options

Front self-hosted A2A endpoints with an identity-aware gateway and an owner_resolver tied to the trusted tenant and subject, or host on Foundry.
