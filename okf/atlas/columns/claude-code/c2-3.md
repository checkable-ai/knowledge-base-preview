## Answer

Covered. Local sandbox runs on macOS, Linux and WSL2 only; native Windows runs commands unsandboxed. Sandbox covers shell commands only. Network domain allowlist starts empty. Cloud and self-hosted environments define other places code runs.

Source statement: "Connections go through a proxy on your machine that checks each host against your allowed domains, which start empty." (https://code.claude.com/docs/en/sandboxing)

Research detail: Local shell commands run in an OS-level sandbox with filesystem and network isolation and a proxy-enforced domain allowlist. Cloud sessions run in isolated Anthropic-managed VMs with configurable network access, or on customer infrastructure through self-hosted environments. Dev containers and the sandbox runtime can wrap the whole process.

<!-- chunk: products -->
## Products

Sandboxed Bash tool, cloud sessions, self-hosted environments, dev containers

<!-- chunk: gaps -->
## Gaps

The proxy does not inspect TLS by default, so broad allowed domains permit exfiltration or domain fronting. No sandbox on native Windows. Hooks, MCP servers and mods run outside the sandbox.

<!-- chunk: options -->
## Options

Use a custom TLS-inspecting proxy and narrow domain lists, and run the whole process in a dev container for higher-risk work.
