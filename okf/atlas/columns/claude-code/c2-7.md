## Answer

Partly covered. File tools, MCP servers and hooks run outside the sandbox, and native Windows is unsandboxed. No documented emergency stop or immediate cut-off of a user's or organisation's access beyond interrupting a session. The customer must contain the whole agent process (container or VM) and provide the access cut-off.

Source statement: "The sandbox covers shell commands only." (https://code.claude.com/docs/en/sandboxing)

Research detail: Shell commands run in an OS-enforced sandbox on macOS, Linux and WSL2 with filesystem limits and a proxy-enforced domain allowlist. Managed settings can make the sandbox admin-required with failIfUnavailable and allowUnsandboxedCommands false, and strictAllowlist or allowManagedDomainsOnly deny hosts outside the list. Cloud sessions run in isolated Anthropic-managed VMs with limited network access. No documented control stops a running session or revokes access at once.

<!-- chunk: products -->
## Products

Sandboxed Bash tool, managed and server-managed settings, cloud session VMs, Claude apps gateway

<!-- chunk: gaps -->
## Gaps

File tools, MCP servers and hooks run outside the sandbox, and native Windows has no sandbox. Server-managed settings refresh hourly. Behind the gateway a revoked user keeps access until the bearer token expires (ttl_hours, default 1 hour).

<!-- chunk: options -->
## Options

Enforce the sandbox through MDM or server-managed settings, lower the gateway ttl_hours, and test how fast IdP removal or a zero spend cap cuts off a live session.
