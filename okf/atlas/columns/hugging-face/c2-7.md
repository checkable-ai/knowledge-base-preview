## Answer

Partly covered. Network access is not limited. Outbound TCP, UDP and loopback access to the control server are not isolated, and no egress allowlist is documented. Detached descendants that call setsid() can outlive process termination. Teardown can fail and leave a billable Job that the customer must reconcile.

Source statement: "Outbound TCP, loopback access to the control server, UDP, kernel IPC, and readable process-list metadata are not isolated." (https://huggingface.co/docs/huggingface_hub/en/concepts/sandbox)

Research detail: Dedicated sandboxes run each workload in its own Job VM, and kill() cancels the Job. Pooled sandboxes confine each workload to its own uid with Landlock, a scrubbed environment, NO_NEW_PRIVS and rlimits, and idle timeouts shut down unused sandboxes and hosts. Outbound TCP stays open in both modes and no egress allowlist is documented.

<!-- chunk: products -->
## Products

Hub Sandboxes (Sandbox and SandboxPool) on HF Jobs

<!-- chunk: gaps -->
## Gaps

The Sandbox API is experimental. Detached processes can outlive a process kill, and teardown can fail and leave a billable Job. Inside a dedicated sandbox the code runs as root alongside the control server.

<!-- chunk: options -->
## Options

Use dedicated sandboxes for untrusted code, cancel the Job as the kill path, and add egress filtering outside Hugging Face.
