## Answer

Not covered. No sandbox limiting an agent's files, processes or network. Key blocking cuts model and tool access but is not sandboxing.

Research detail: The Agent Kill Switch stores a shutdown webhook on each registered agent, and a proxy admin fires it from the Admin UI Danger Zone or POST /v1/agents/{agent_id}/kill_switch. Every fire is written to the audit log. Virtual keys can be blocked through /key/block to cut an agent off from models and MCP tools, and iteration budgets cap LLM calls and spend per session. Model-generated code can run in an e2b or opensandbox sandbox through the code interpreter interceptor, and the agent harness offers a Docker sandbox.

<!-- chunk: products -->
## Products

Agent Kill Switch, /key/block, Agent Iteration Budgets, Sandbox code interpreter interceptor (e2b, opensandbox), harness sandbox.docker

<!-- chunk: gaps -->
## Gaps

The kill switch only calls the agent's own runtime, and LiteLLM leaves the agent registered and enabled, so the stop depends on that runtime honouring the webhook. Sandboxing is delegated to e2b, opensandbox or Docker, and sandbox.local runs with the user's permissions. Python tools in Tool Loop and Deep Agents run in-process, outside the sandbox. No egress policy for the agent's own runtime.

<!-- chunk: options -->
## Options

Pair the kill switch with a /key/block on the agent's virtual key, and time how quickly in-flight model and MCP calls fail.
