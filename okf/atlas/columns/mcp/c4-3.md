## Answer

Covered. HTTP transports using MCP authorization. Servers that call upstream APIs must obtain their own separate token. Propagation to downstream systems beyond the MCP server is not defined by the specification.

Source statement: "The Model Context Protocol provides authorization capabilities at the transport level, enabling MCP clients to make requests to restricted MCP servers on behalf of resource owners." (https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/index.md)

Research detail: Clients obtain OAuth 2.1 tokens on behalf of the resource owner, and servers that call upstream APIs MUST obtain a separate token rather than pass the client token through. The Enterprise-Managed Authorization extension carries the enterprise user identity through an ID-JAG grant. The core specification does not define token exchange down a chain of services.

<!-- chunk: products -->
## Products

MCP Authorization, Enterprise-Managed Authorization extension

<!-- chunk: gaps -->
## Gaps

No defined propagation of user identity past the MCP server. The extension is opt-in.

<!-- chunk: options -->
## Options

Pair MCP authorisation with OAuth token exchange at the server for downstream calls.
