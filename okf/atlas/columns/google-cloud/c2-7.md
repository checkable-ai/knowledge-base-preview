## Answer

Not covered. No documented emergency stop or immediate access cut-off for an agent, and no configurable file or process limits. Runtime sandbox isolation, VPC Service Controls egress prevention and TTL expiry fall short.

Research detail: Agent Platform Sandbox isolates each sandbox from other sandboxes and the host, restricts operations inside it, and lets VPC Service Controls perimeters block egress. Agent Runtime agents run in a Google-managed network with no route to the customer VPC unless a Private Service Connect interface is attached, and inside a VPC Service Controls perimeter their default internet access is blocked. Agent Gateway applies a default-deny policy to outgoing traffic, so destinations need Agent Registry entries and an authorisation policy. Deleting a deployed agent invalidates its agent identity, and IAM roles can be removed from an agent's service account.

<!-- chunk: products -->
## Products

Agent Platform Sandbox, Agent Runtime with Private Service Connect interface, VPC Service Controls, Agent Gateway and Agent Registry, agent delete and IAM role revocation

<!-- chunk: gaps -->
## Gaps

The sandbox page does not describe filesystem policy or how a sandbox is terminated, and sandboxes persist for 7 to 14 days by TTL. The delete page does not say how deletion affects running sessions or in-flight requests, and stale IAM policy principals remain until removed. No single documented control stops all running agents at once.

<!-- chunk: options -->
## Options

Run agents inside a VPC Service Controls perimeter with egress only through Agent Gateway. Test deletion and role removal during a live session and time how quickly calls fail. Script a project-level IAM deny or org policy as an emergency stop and rehearse it.
