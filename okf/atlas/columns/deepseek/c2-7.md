## Answer

Partly covered. No network or process containment. The sandbox page says network and process visibility are outside its scope. There is no documented emergency stop, kill switch or access cut-off for a running agent. The only signal cancels policy resolution before a command launches.

Source statement: "SandboxMode governs filesystem effects only." (https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/sandbox.md)

Research detail: The open-source DeepSeek Harness confines subprocesses with a sandbox in read-only, workspace-write or danger-full-access file-effect modes, using Linux bwrap and Landlock, macOS Seatbelt or a Windows restricted token. An approval policy of ask or never gates each action, and denied or unanswerable approvals fail closed. The hosted API offers no execution containment.

<!-- chunk: products -->
## Products

DeepSeek Harness sandbox, approval policy, permission presets

<!-- chunk: gaps -->
## Gaps

The sandbox governs filesystem effects only, and the docs say network and process visibility are outside it. Enforcement can be reported as partial, notably on Windows and older Linux kernels. The repository states Harness is developer preview, has not had a security audit and does not guarantee isolation. No kill switch for a running agent was found.

<!-- chunk: options -->
## Options

If Harness is used, run it in a disposable VM or container with an egress proxy and treat its sandbox as one layer only.
